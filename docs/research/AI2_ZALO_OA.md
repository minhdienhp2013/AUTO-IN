## CODE-402 follow-up — synthetic signed structured postback (13/10/2026)

- `SyntheticFixtureNormalizer` (called **after** synthetic verifier) now accepts a separate fixture `kind:"postback"` with **exactly** `confirmation_postback:{kind:"verified_confirmation_accept",challenge_id:<canonical UUID>,challenge_token:<43-char canonical base64url of 32 random bytes>}`. No text/file/filename/MIME on a postback, no extra or missing challenge fields. Wrong structure, oversized/short/noncanonical token and text/file fields **on a `kind:"postback"` fixture** are **422 INVALID_WEBHOOK**. ## AI2 follow-up — provider event id and late-event ordering (2026-10-29)

- Zalo Support's written reply states `event_id` is used to identify retries/idempotent delivery, and `timestamp` is provided so a server can reorder late events. AI2 now stores `event_id` in `zalo_official_quarantine.provider_event_id`, protected by migration 005 partial uniqueness on `(oa_id,provider_event_id)`. The old `provider_claimed_event_id` is retained for compatibility and is deliberately not backfilled/indexed because legacy values may be `message.msg_id`. Pre-005 exact-byte repeats still dedupe by existing `(oa_id,raw_sha256)`.
- The adapter and SQL fixture have a regression for same `event_id` with different JSON whitespace/serialization: return the original receipt, do not add a second row, and do not persist file URL/name/body. PostgreSQL tests were updated to apply 005 and cover the same case, but were **SKIPPED** here because no test database URL was configured. AI0 must register 005 before enabling any route.
- Timestamp handling: `official-webhook.ts` persists the body `timestamp` as `InboundEvent.occurred_at`. However, the durable batch queue orders by database `received_at` and passes `server_received_event_ids`; `conversation/processor.ts` deliberately honors that receive-order list over `occurred_at`. Thus late provider events are recorded with their provider timestamp but are **not reordered by provider time in the live durable path**; late arrivals after a batch is formed can be processed in a later batch. Changing this needs an explicit contract for late-event window/rebatching and an ordering contract change across AI2 queue + conversation processor; AI1/Core was not changed here.
