## Candidate binding and current route

- `backend/integrations/zalo/official-webhook.ts` implements the documented formula using the exact raw JSON body and server OA configuration. Its comment/test labels raw-body serialization as unverified. The ±5-minute timestamp window is a local app policy, not a documented Zalo replay horizon or media TTL.
- `backend/integrations/zalo/official-quarantine.ts` sends unsupported file events that pass the local formula verifier to `zalo_official_quarantine`; it does not persist the attachment URL/bytes or insert a normal `zalo_inbound_events` file row. The verifier's raw-body assumption remains unconfirmed by Zalo. Quarantine deduplicates by `(oa_id, raw_event_sha256)`, and its provider-claimed `msg_id` is only a manual correlation hint.
- `backend/composition/pilot-private-source.ts` is the existing private storage port. It requires a matching normal file event and OA→shop registry before sealing. The stored row binds `(shop, OA, event, customer, conversation, format, artifact_ref, SHA-256, size)`; it recomputes SHA-256 and reads the object back. `backend/composition/pilot-ingress.ts` binds the source artifact to exactly one current order/revision/request hash and settings, and checks code text events against the same OA/customer/conversation before constructing the code submission.
- `backend/conversation/pilot-word-pdf-intake.ts` now seals event-keyed bytes before returning `WAITING_FOR_SETTINGS`, so a file-first conversation can retain its source while code/settings arrive later. Code-only input returns `WAITING_FOR_FILE`; the adapter rejects mixed identity, bad bytes, oversize input, and custody readback mismatch before Core ports. It accepts no caller URL/path. The 25 MiB cap is an application limit, not a Zalo inbound limit.
- `backend/server.ts` only installs the synthetic Zalo webhook in this candidate. Without it the default route is unavailable; pilot private-source configuration does not enable a real OA adapter. The synthetic PostgreSQL integration test pre-binds fixture data and is not proof of a real webhook signature, provider download, or attachment provenance.

The current source row is keyed by `(oa_id,event_id)` and has no attachment id/index. Zalo's webhook exposes `attachments` as an array. Therefore the live parser must reject multiple/ambiguous attachments and preserve the exact selected attachment before this registry is usable. The event-keyed storage cannot disambiguate two attachments under one message event. In addition, the AI2 adapter receives a caller-selected list of persisted event ids and only binds to an order/revision already present in Core. The synthetic PG test creates that draft/order and pre-binds its plan; there is no verified real-ingress conversation batcher/order resolver wired here. AI2 must not infer these links from timing or create Core orders itself.

## Decision and required confirmation

**Live transport stays unwired / NO-GO.** The current ingress holds file events in quarantine, so the existing source-custody table cannot yet accept a real OA file event. Do not promote the file URL or MD5 into a trusted source. Code candidates and file bytes must not be joined by filename, MIME, URL, shared customer text, or timing. Synthetic intake may exercise only injected verified-event/media/custody ports; it does not establish provider authenticity. Even after Zalo confirms signature and media retrieval, AI0/AI1 must explicitly approve an attachment-to-event key (single attachment only, or a stable attachment id/index in the source registry) and provide a durable conversation event selector plus existing-order/revision resolver. No queue/schema change was made in this AI2 task.

Before AI0 can connect a live file event to private custody, Zalo must provide (or confirm from official test material): (1) a signed webhook test vector, including exact `data` bytes/serialization and timestamp used in the MAC; (2) supported inbound retrieval URL/endpoint, auth/token scope, allowed host and redirect rules, DNS/TLS requirements; (3) URL expiry/refresh and documented HTTP/error/retry behavior; (4) inbound size/format limits and the binding guarantee between signed `(OA,event,attachment)` and returned bytes; (5) integrity expectations beyond provider MD5, including a testable byte/hash vector. The owner must also supply an OA test account, app/OA permissions and test credentials through a secret channel. No such account, OA credentials, or Zalo-signed vector was available in this task.

Still separately unverified: production filesystem ACL/reparse safety on the deployment host and TN-011 retention/cleanup. Do not enable the existing private store for customer files until those are approved and tested. No Core/schema/queue changes were made; any request for a new event-to-source contract or queue trigger goes to AI0.
